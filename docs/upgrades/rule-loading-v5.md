# 规则按需加载与自动迁移升级手册（桥接协议 v6）

适用于已经使用 `manage-obsidian-project-kb`，希望将现有项目与 Obsidian Vault 升级到“常驻规则 + 条件规则”加载方式的用户。

当前 **v6 指 AGENTS 桥接协议版本**，不是 GitHub Release 标签或配置版本。本页沿用原 v5 文件地址，避免已有链接失效。配置目标仍为 `Schema_Version: 2`。无需重建 Vault、删除配置或重新生成历史笔记。

**同一台电脑、同一份全局 Skill 只需升级一次。** 一次启用自动迁移后，其他已初始化项目在后续使用该 Skill 开发时自行迁移；不需要每个项目再输入 `/kb-upgrade`，也不会重复下载 Skill。

## 旧用户升级入口：直接复制这段话

**旧版 Skill 没有 `/kb-upgrade` 定义，不能用这个命令完成首次升级。** 在代码项目目录打开 Agent，直接发送下面的普通提示词；不需要旧 Skill 先识别新命令，也不需要手动替换仓库地址：

```text
请从 https://github.com/yqbo00/manage-obsidian-project-kb
的 master 分支获取最新版完整 Skill，更新当前客户端实际使用的
manage-obsidian-project-kb 安装副本。修改前备份，保留本地定制。

随后重新读取安装后的 SKILL.md 和 references/upgrade.md，
确认新版已定义 /kb-upgrade，再继续完成当前项目桥接、关联 Shared
和项目知识库规则的升级，并验证结果。

同时启用并保存本机当前安装的自动迁移授权：后续在其他已初始化
项目使用这份 Skill 且允许写入时，自动完成本次协议的桥接和规则
兼容迁移；只读任务只检查，不扫描所有仓库，不重复下载安装。

不要仅执行旧版 /kb-init，也不要在下载安装新版后停止。
无法确定的规则保留原状，最后报告实际加载路径、获取的提交 ID、
桥接版本、已完成的迁移和剩余事项。
```

仓库中的 Skill 包路径为 `skills/manage-obsidian-project-kb/`。需要完整更新其中的资源，不能仅替换 `SKILL.md`。本入口明确使用 `master` 分支；Agent 应记录实际获取的提交 ID，不能把旧 Release、业务仓库的 origin 或缓存副本当成本次目标版本。

这个请求让 Agent 连续完成“安装新版 → 重新读取新版流程 → 升级项目与知识库”，用户无需逐步接力。需要访问网络和写入权限时，按客户端的实际审批提示处理；安装失败应明确报告，不能自动退回旧版 `/kb-init` 后声称完整升级成功。

## 已升级用户：使用快捷指令

确认实际安装的新版已包含 `/kb-upgrade` 和 `references/upgrade.md` 后，后续可以发送：

```text
使用 manage-obsidian-project-kb 执行 /kb-upgrade --auto-migrate
```

这一次更新全局安装、处理当前项目与关联 Shared，并保存自动迁移授权。之后进入 B、C 等已初始化项目正常开发即可；它们实际加载同一份新版 Skill 时自动检查和迁移，Shared 已完成且未变化时不重复写入。不会提前扫描其他仓库。不同客户端共用同一物理 Skill 目录时共享此状态；其他机器或独立安装仍各需更新一次。

只想更新当前安装和当前项目，不启用后续自动迁移，可省略 `--auto-migrate`。已经启用的授权不会因省略选项而被关闭；需要关闭时说“关闭当前安装的知识库自动迁移”，无需卸载 Skill。

`/kb-upgrade` 是 Agent 工作流指令，不是独立安装程序；需要可用文件工具，以及更新远程包所需的网络/权限。来源无法核实时会明确报告 Pending，不会假称“已更新到最新版”。如果只想预览影响，使用 `/kb-upgrade --check`。

以下章节用于了解流程、排查或手动分步升级，正常用户无需逐项操作。

## 升级后会发生什么

- `Mandatory` 表示命中适用条件后必须遵守；`applies_to: ["*"]` 仅表示跨项目适用。
- `load: Always` 表示适用项目内常驻加载；`load: Conditional` 通过 `triggers` 决定何时读取规则正文。
- 任务范围、目标路径或计划操作变化时，Agent 重新筛选并补读规则。
- Rule Catalog 保存来源与适用条件摘要；来源笔记仍是权威副本，目录遗漏不能使规则失效。
- 普通知识的检索篇数限制不适用于已命中的规则。
- 旧 Mandatory 缺少 `load` 时仍完整加载，避免升级后静默漏读。

**仅复制新版 Skill 或执行 `/kb-init`，不等于已授权规则迁移。** 使用上面的一次升级入口后，明确条件的旧规则由升级/自动迁移流程整理；无法确定的规则保留兼容加载并集中报告，不会为追求减少加载而猜测或降级。

## 执行范围与顺序

| 步骤 | 用户操作 / 自动执行 | 完成标志 |
|---|---|---|
| 更新完整 Skill 包并启用自动迁移 | 用户在任意一个项目请求一次；每份独立安装一次 | 实际包完整，本机授权记录读回成功 |
| 更新项目桥接 | 后续使用该项目时自动执行，不重新安装 | 适用的标准桥接块为 version 6，配置与 Vault 关联正确 |
| 整理共享规则 | 首个关联项目自动处理，后续按实际差异跳过 | 常驻/条件规则明确，Shared Rule Catalog 与来源一致 |
| 整理项目规则 | 后续使用该项目时自动执行 | 项目/模块规则条件明确，Dashboard Rule Catalog 同步 |
| 验证实际行为 | 每次实际迁移后由 Agent 核对 | 无关规则不读全文，相关规则与旧兼容规则不漏读 |

建议在一个活跃项目发出一次升级请求，之后照常开发。自动流程遵循现有写锁、备份、最小修改与去重机制；共享层变化会影响关联项目，独立安装的旧客户端仍应更新。所有项目尚未实际使用前，不能把结果说成“所有项目已迁移”。

### 自动触发的边界

- 必须实际加载新版 Skill。旧桥接已经调用 Skill 时能进入新流程；客户端缓存旧版时需刷新/新会话，桥接缺失时需显式调用一次 Skill。单纯打开目录不会运行后台服务。
- 只读审查、查询和 `/kb-upgrade --check` 不修改任何文件，待下次允许写入的任务再迁移。未初始化项目仍需选择 Vault 和项目名，不会自动绑定。
- 本机授权保存在状态目录的 `manage-obsidian-project-kb/installations.json`（POSIX 默认 `~/.local/state/`，支持绝对 `XDG_STATE_HOME`；Windows 使用 `%LOCALAPPDATA%`）。它独立于 Skill 包，按实际物理安装路径区分，不提交到 Git、不写入同步 Vault。
- 授权只覆盖本次兼容协议，不是未来任意改动的通行证。没有有效记录或权限不足时明确报告未启用/Pending；正常任务不会替用户偷偷开启。
- 有歧义的规则不会反复逐条弹出询问；保留兼容加载并汇总。无差异时不重写、不备份、不产生工作日志。

## 可选：手动分步与故障排查

**以下 1–5 节不是每个项目必做的升级清单。** 仅用于未启用自动迁移、需要限制修改范围或排查失败项的用户。

## 1. 更新客户端安装的 Skill

从本仓库包含本手册及 `references/rule-loading.md` 的版本获取完整目录：

```text
skills/manage-obsidian-project-kb/
```

发布者应在 Release 中链接实际包含本次变更的标签或提交。本手册的一句话入口明确使用 `master`；选择固定 Release 的用户需确认其中包含 `/kb-upgrade` 与 `references/upgrade.md`，不要仅凭桥接 v5 判断是否包含升级命令。Git 安装用户先检查本地修改，再更新到目标版本，避免覆盖自己的定制。

先备份当前安装目录，再按安装方式更新：

- **软链接安装**：更新软链接指向的仓库版本，确认客户端仍指向该目录。
- **复制安装**：更新完整 Skill 包，包括 `SKILL.md`、`assets/`、`references/` 和 `agents/`，不要只替换入口文件。将旧版备份放到客户端不会扫描为 Skill 的位置。
- **客户端导入安装**：用原客户端的导入/刷新功能更新；独立复制的导入不会随另一个客户端自动更新。
- **项目内安装**：检查该项目是否还有同名旧副本；不要仅更新用户级副本后就假定所有会话已使用新版。

客户端安装入口见 [README 安装说明](../../README.md#安装)。安装位置以客户端实际配置为准。

打开新的项目会话，用客户端支持的方式显式调用 Skill，要求 Agent 报告它实际读取的 `SKILL.md` 路径，并确认存在 `references/rule-loading.md`、标准桥接模板包含：

```html
<!-- kb:agents-bridge:version=6 -->
```

如果更新未被识别，刷新客户端或重启后再检查。同名 Skill 不应被假定会自动合并。

## 2. 手动更新指定项目桥接（自动流程失败时）

在**代码仓库根目录**启动 Agent。下面都是发送给 Agent 的自然语言提示词，`/kb-*` 是本 Skill 的逻辑指令，不是终端 Shell 命令。先使用客户端支持的方式选中 `manage-obsidian-project-kb`，再发送：

```text
使用 manage-obsidian-project-kb 升级当前已初始化项目的知识库桥接。

1. 读取现有 .ai/obsidian-kb.json，沿用 Vault、项目名及已配置客户端。
2. 执行 /kb-init，将适用的标准桥接区块更新到 version 6。
3. 修改前备份；保留非托管指令，不批量改写历史规则和知识笔记。
4. 执行 /kb-doctor，报告配置、桥接和规则目录问题。
5. 再执行一次 /kb-init，验证无差异的配置和桥接没有被重写、
   没有重复插入区块或生成无效备份。

最后报告实际 Skill 路径、配置版本、每个桥接目标的状态和未解决问题。
```

预期结果：

- Schema 2 保持不变；Schema 0/1 按现有初始化协议备份后迁移到 2。
- Codex/ZCode 等共用的 `AGENTS.md` 只维护一个标准区块；启用 Codex 且存在非空 `AGENTS.override.md` 时，同步其中的区块。
- 导入型客户端检查其导入声明和被导入的标准桥接；不要要求每个导入文件都出现 version 6 标记。
- 旧规则的强度与加载条件保持原状。Catalog 缺失可被诊断为待整理，不代表需要重建知识库。
- Vault 路径或项目名不符时先修正绑定问题，不把另一个项目的配置当作当前项目使用。

普通升级不需要 `/kb-init --reconfigure`。需要改变客户端集合时才使用 `/kb-init --agents`。不要为通过初始化而删除旧配置、重复标记或归属不明的写锁；先根据诊断定位具体问题。

## 3. 整理 Shared 共享规则

同一 Vault 只需整理一次，可从任意一个已正确关联它的项目会话执行。先对将修改的 Shared 笔记与索引建立可恢复备份或本地版本快照；备份也应保留在私有位置，不要为了备份而公开知识库内容。

```text
使用 manage-obsidian-project-kb，按新版 rule-loading 协议整理当前 Vault 的 Shared。
本次授权修改共享规则笔记和对应索引。

先建立可恢复备份，再逐条执行：
- 区分 Rule、Contract、ADR、Runbook、Knowledge、Asset。
- 依据原文已有的适用条件，为规则补齐 kind、load 和必要的 triggers。
- 仅跨任务稳定适用的少量规则保留 Always；其余使用明确的 Conditional。
- 保持原有行为要求、约束强度和项目范围，不自动降级 Mandatory。
- 不明确的条件保留兼容加载，列出待确认项。
- 非规则笔记保留工程知识结构；不得仅靠改 kind 绕过原有 Mandatory。
- 不删除历史内容，不自动合并、废弃规则或扩大适用范围。
- 同步 Shared Index 的 Rule Catalog，追加 Change Log，读回验证。

最后执行 /kb-doctor，列出常驻规则、条件规则和仍兼容加载的旧规则，
说明哪些修改已生效、哪些存在歧义，以及备份位置。
```

下面是规则加载字段的局部示例，不是完整笔记模板：

```yaml
kind: Rule
status: Active
applies_to: ["*"]
enforcement: Mandatory
load: Conditional
triggers:
  - "准备在同一工作目录同时运行两个或以上构建命令"
```

多个 trigger 条目为 OR；需要同时满足的条件应在一条中明确写出。不要把所有旧 Mandatory 机械改为 Conditional，也不要用含糊的“相关时”“需要时”作为触发条件。正文中的适用条件必须与元数据一致。

## 4. 整理各项目的规则

仅在选择手动整理时，在目标项目会话发送（已启用自动迁移的用户无需逐项目发送）：

```text
使用 manage-obsidian-project-kb，按新版协议整理当前项目知识库中的项目／模块规则。
本次授权修改当前项目的规则笔记和 Dashboard Rule Catalog。

先建立可恢复备份，依据原有内容补齐类型、加载时机和触发条件，
保持原有行为要求、强度与实际适用范围，不改变历史事实。
ADR、Runbook 和排错记录保留各自结构；临时范围、阶段例外、待办和阻塞
继续留在事项文档、Sprint、Worklog，不升级为全局规则。
含义不明确的规则保持原状并报告，不修改其他项目，也不重新整理 Shared。
同步来源、Change Log 和 Catalog，读回验证并报告结果。
```

目录结构不需要重建。可以先整理当前活跃模块，其他规则保持兼容；不要求一次补齐所有历史笔记。授权范围中的实际知识变更按 Skill 规则记录 Worklog，纯诊断和场景推演不记成完成成果。

## 5. 验收是否达到预期

先开新会话进行只读验证，避免旧会话中已经加载的全文影响判断：

```text
使用 manage-obsidian-project-kb，只读验证当前项目的规则加载。

分别以“检查 README 文案”“修改鉴权接口”“准备数据库迁移”为场景，
报告应加载的规则来源和原因、明确不适用的条件规则，以及未解决的兼容项。
再检查任务从文档查询转为迁移规划时，是否会补读新命中的规则。
核对来源与 Catalog，区分实际读取结果和场景推演结论。
不要修改文件，不运行构建、部署或迁移，不写 Worklog。
```

| 检查项 | 通过标准 |
|---|---|
| 文档任务 | 已明确不适用的构建/部署/迁移规则不读全文；常驻和旧兼容规则仍读取 |
| 范围变化 | 新增鉴权、构建或迁移操作前，补读实际命中的规则 |
| 规则完整性 | Catalog 漏项/过期不能隐藏来源规则；命中超过 5 条时不截断 Mandatory |
| 不明确条件 | 报告歧义并读取来源确认，不能默认“不适用”或伪称已遵守 |
| 幂等初始化 | 重复执行时，无差异配置和桥接零写入、零重复区块、零无效备份 |
| 跨项目自动迁移 | A 项目启用后，B 项目可写任务加载同一安装时自动迁移；不联网、不重装，不扫描 C 项目 |
| 只读与未初始化项目 | 只读任务不写锁/日志/备份；未初始化项目不根据全局记录猜测 Vault |
| 重试与部分失败 | Shared 一致时跳过；来源已迁移但 Catalog 未同步时修复 Catalog；失败保留 Pending |
| 授权关闭/缺失 | 不迁移、不偷偷启用；仍按旧 Mandatory 兼容策略读取 |
| 日常完成同步 | 在后续真实开发任务完成后，用 `/kb-status`、`/kb-today` 核对任务状态和结果证据 |

验收以相关规则是否命中、无关正文是否减少为准，不承诺固定的 token 降幅或“绝对不会遗漏”。元数据发现仍有读取成本。结构校验只能检查 Skill 包格式，不能代替实际客户端行为验证；Markdown 也不能替代账号权限、CI 契约检查等执行控制。

## 常见问题

**全局安装为什么还要每个项目升级？**

不需要每个项目手动升级。包只更新一次；项目内的桥接和 Vault 内的项目规则是不同文件，仍需迁移，但新版会在实际使用时自动处理。一次使用上述入口并成功保存授权即可。若只是复制了新版包、尚未启用自动迁移，只需再发一次“启用当前安装的自动迁移”，不必逐项目操作或重新下载。

**怎样确认自动迁移真的启用了？**

升级结果应包含实际安装路径、版本/提交、本机授权记录位置和启用状态，以及“其他项目使用时迁移”。只报告“文件已下载”或“当前项目桥接已更新”不足以证明已启用。可要求只读核对这些项目，不会生成测试日志或备份。

**Agent 说没有 `/kb-upgrade`，准备改用 `/kb-init`，怎么办？**

它尚未读取到包含升级命令的 Skill。直接发送本文开头的旧用户升级提示词，让它先获取并安装完整新版，再读取实际安装路径下的新指令。旧版 `/kb-init` 可更新其已知的配置和桥接，但不会因此获得新版本的规则迁移流程，不能代替完整升级。即使之前已经运行过 `/kb-init`，也可以继续按这个入口升级，已完成且无差异的部分应保持不变。

**为什么下载安装后仍然说命令不存在？**

检查 Agent 实际读取的 `SKILL.md` 路径及是否包含 `/kb-upgrade`。可能更新了仓库副本，却仍使用另一个客户端/项目内安装，或者会话继续沿用旧指令。让 Agent 重新读取实际安装文件；客户端无法刷新时，在更新完成后重启会话再调用。不要凭“已下载”就判断新版已经生效。

**升级需要 `.codex/project.yaml` 吗？**

不需要。本 Skill 的项目绑定文件是代码项目根目录下的 `.ai/obsidian-kb.json`。不要因为缺少无关的项目卡而创建替代配置、改变 Vault 绑定或跳过升级。

**更新了 Skill，为什么每次还是读很多？**

检查实际加载的 Skill 路径、项目桥接版本和旧 Mandatory 数量。旧规则没有 load 时会继续全文读取；仅升级桥接不会完成规则迁移。还要检查客户端的其他指令文件是否保留了旧的“每次全部加载”要求，定位后按其管理边界处理，不直接覆盖用户指令。

**`/kb-doctor` 没有自动修好 Catalog？**

它是只读诊断。使用第 3/4 步的明确整理任务进行来源与索引同步，不只修改 Catalog 来改变实际约束。

**能否一次更新所有项目？**

可以让 Agent 按你明确列出的项目路径逐个处理。每次重新读取该项目配置，逐项记录成功/失败；多个 Vault 的 Shared 分别整理，同一个 Shared 不重复迁移。先完成一个项目的验收，再推广。

## 部分失败与回退

- 保留每次升级的文件清单、备份位置和未完成项。某个目标失败时只重试该范围，不把部分成功报告为整体成功。
- 仅 Skill/桥接升级需要回退时，恢复已备份的完整 Skill 包，并恢复对应项目的托管桥接区块；如果文件已有后续用户修改，按差异恢复区块，不能整文件覆盖新内容。
- 已整理过规则时，回退客户端不会撤销知识库变化。旧客户端可能忽略 Conditional 而重新加载全部 Mandatory。需要回退知识时，按变更清单恢复相关元数据、正文与 Catalog，并保留迁移后的快照及审计说明。
- 不用旧 Vault 全量覆盖来修复少数规则，也不删除原始历史。回退后重新执行只读诊断，核对实际加载路径和配置兼容性。
