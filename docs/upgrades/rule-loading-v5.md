# 规则按需加载升级手册（桥接协议 v5）

适用于已经使用 `manage-obsidian-project-kb`，希望将现有项目与 Obsidian Vault 升级到“常驻规则 + 条件规则”加载方式的用户。

本文的 **v5 指 AGENTS 桥接协议版本**，不是 GitHub Release 标签或配置版本。配置目标仍为 `Schema_Version: 2`。无需重建 Vault、删除配置或重新生成历史笔记。

## 推荐：一句话升级

在代码项目目录打开 Agent，发送：

```text
使用 manage-obsidian-project-kb 执行 /kb-upgrade
```

这一个请求会让 Agent 完成版本检查、完整 Skill 更新、当前项目桥接更新、Shared 与项目规则的保守整理及验收。用户不必依次输入下文的每一步。来源不明时补充一次发布地址；沙箱要求权限时按客户端提示授权。

旧版 Skill 还不认识 `/kb-upgrade` 时，直接发送下面的通用提示词，将占位内容换成本项目的 GitHub 地址或目标 Release 链接：

```text
请从 <本项目的 GitHub 地址或目标 Release 链接> 更新我当前客户端实际使用的
manage-obsidian-project-kb 完整 Skill 包。先备份并保留本地定制。
安装后读取新版指令，接着执行 /kb-upgrade，完成当前项目桥接、关联 Shared
和项目规则的兼容升级与验收，不要只下载安装包后停止。
无法确定的规则保留原状，最后汇总剩余事项。
```

默认只处理当前项目与其关联 Shared。多个项目可在同一次请求中列出明确路径，Agent 应逐个处理；已升级且未变化的 Shared 自动跳过重复写入。其他机器或独立客户端安装仍需在对应环境触发升级。

`/kb-upgrade` 是 Agent 工作流指令，不是独立安装程序；需要可用文件工具，以及更新远程包所需的网络/权限。来源无法核实时会明确报告 Pending，不会假称“已更新到最新版”。如果只想预览影响，使用 `/kb-upgrade --check`。

以下章节用于了解流程、排查或手动分步升级，正常用户无需逐项操作。

## 升级后会发生什么

- `Mandatory` 表示命中适用条件后必须遵守；`applies_to: ["*"]` 仅表示跨项目适用。
- `load: Always` 表示适用项目内常驻加载；`load: Conditional` 通过 `triggers` 决定何时读取规则正文。
- 任务范围、目标路径或计划操作变化时，Agent 重新筛选并补读规则。
- Rule Catalog 保存来源与适用条件摘要；来源笔记仍是权威副本，目录遗漏不能使规则失效。
- 普通知识的检索篇数限制不适用于已命中的规则。
- 旧 Mandatory 缺少 `load` 时仍完整加载，避免升级后静默漏读。

**仅更新 Skill 或执行 `/kb-init`，不会自动把旧规则改成条件加载。** 要获得减少无关正文加载的效果，还需要完成规则整理。

## 执行范围与顺序

| 步骤 | 执行范围 | 完成标志 |
|---|---|---|
| 更新完整 Skill 包 | 每台机器、每份独立客户端安装 | 实际加载路径指向新版，存在 `references/rule-loading.md` |
| 更新项目桥接 | 每个代码项目 | 适用的标准桥接块为 version 5，配置与 Vault 关联正确 |
| 整理共享规则 | 同一个 Vault 的 Shared 层一次 | 常驻/条件规则明确，Shared Rule Catalog 与来源一致 |
| 整理项目规则 | 每个项目的知识目录 | 项目/模块规则条件明确，Dashboard Rule Catalog 同步 |
| 验证实际行为 | 先试点项目，再推广到其他项目 | 无关规则不读全文，相关规则与旧兼容规则不漏读 |

建议先选一个活跃项目完成全过程。Shared 的修改会影响所有关联项目，不要让多个 Agent 同时迁移同一共享层；共享该 Vault 的其他客户端也应先升级 Skill 与桥接。

## 1. 更新客户端安装的 Skill

从本仓库包含本手册及 `references/rule-loading.md` 的版本获取完整目录：

```text
skills/manage-obsidian-project-kb/
```

发布者应在 Release 中链接实际包含本次变更的标签或提交；本文不假定特定标签名或默认分支。Git 安装用户先检查本地修改，再更新到目标版本，避免覆盖自己的定制。

先备份当前安装目录，再按安装方式更新：

- **软链接安装**：更新软链接指向的仓库版本，确认客户端仍指向该目录。
- **复制安装**：更新完整 Skill 包，包括 `SKILL.md`、`assets/`、`references/` 和 `agents/`，不要只替换入口文件。将旧版备份放到客户端不会扫描为 Skill 的位置。
- **客户端导入安装**：用原客户端的导入/刷新功能更新；独立复制的导入不会随另一个客户端自动更新。
- **项目内安装**：检查该项目是否还有同名旧副本；不要仅更新用户级副本后就假定所有会话已使用新版。

客户端安装入口见 [README 安装说明](../../README.md#安装)。安装位置以客户端实际配置为准。

打开新的项目会话，用客户端支持的方式显式调用 Skill，要求 Agent 报告它实际读取的 `SKILL.md` 路径，并确认存在 `references/rule-loading.md`、标准桥接模板包含：

```html
<!-- kb:agents-bridge:version=5 -->
```

如果更新未被识别，刷新客户端或重启后再检查。同名 Skill 不应被假定会自动合并。

## 2. 在每个代码项目更新桥接

在**代码仓库根目录**启动 Agent。下面都是发送给 Agent 的自然语言提示词，`/kb-*` 是本 Skill 的逻辑指令，不是终端 Shell 命令。先使用客户端支持的方式选中 `manage-obsidian-project-kb`，再发送：

```text
使用 manage-obsidian-project-kb 升级当前已初始化项目的知识库桥接。

1. 读取现有 .ai/obsidian-kb.json，沿用 Vault、项目名及已配置客户端。
2. 执行 /kb-init，将适用的标准桥接区块更新到 version 5。
3. 修改前备份；保留非托管指令，不批量改写历史规则和知识笔记。
4. 执行 /kb-doctor，报告配置、桥接和规则目录问题。
5. 再执行一次 /kb-init，验证无差异的配置和桥接没有被重写、
   没有重复插入区块或生成无效备份。

最后报告实际 Skill 路径、配置版本、每个桥接目标的状态和未解决问题。
```

预期结果：

- Schema 2 保持不变；Schema 0/1 按现有初始化协议备份后迁移到 2。
- Codex/ZCode 等共用的 `AGENTS.md` 只维护一个标准区块；启用 Codex 且存在非空 `AGENTS.override.md` 时，同步其中的区块。
- 导入型客户端检查其导入声明和被导入的标准桥接；不要要求每个导入文件都出现 version 5 标记。
- 旧规则的强度与加载条件保持原状。Catalog 缺失可被诊断为待整理，不代表需要重建知识库。
- Vault 路径或项目名不符时先修正绑定问题，不把另一个项目的配置当作当前项目使用。

普通升级不需要 `/kb-init --reconfigure`。需要改变客户端集合时才使用 `/kb-init --agents`。不要为通过初始化而删除旧配置、重复标记或归属不明的写锁；先根据诊断定位具体问题。

## 3. 整理 Shared 共享规则

同一 Vault 只需整理一次，可从任意一个已正确关联它的项目会话执行。先对将修改的 Shared 笔记与索引建立可恢复备份或本地版本快照；备份也应保留在私有位置，不要为了备份而公开知识库内容。

```text
使用 manage-obsidian-project-kb，按新版 rule-loading 协议整理当前 Vault 的 Shared。
本次授权修改共享规则笔记和对应索引。

先建立可恢复备份，再逐条执行：
- 区分 Rule、Contract、ADR、Runbook、Knowledge、Asset。
- 依据原文已有的适用条件，为规则补齐 kind、load 和必要的 triggers。
- 仅跨任务稳定适用的少量规则保留 Always；其余使用明确的 Conditional。
- 保持原有行为要求、约束强度和项目范围，不自动降级 Mandatory。
- 不明确的条件保留兼容加载，列出待确认项。
- 非规则笔记保留工程知识结构；不得仅靠改 kind 绕过原有 Mandatory。
- 不删除历史内容，不自动合并、废弃规则或扩大适用范围。
- 同步 Shared Index 的 Rule Catalog，追加 Change Log，读回验证。

最后执行 /kb-doctor，列出常驻规则、条件规则和仍兼容加载的旧规则，
说明哪些修改已生效、哪些存在歧义，以及备份位置。
```

下面是规则加载字段的局部示例，不是完整笔记模板：

```yaml
kind: Rule
status: Active
applies_to: ["*"]
enforcement: Mandatory
load: Conditional
triggers:
  - "准备在同一工作目录同时运行两个或以上构建命令"
```

多个 trigger 条目为 OR；需要同时满足的条件应在一条中明确写出。不要把所有旧 Mandatory 机械改为 Conditional，也不要用含糊的“相关时”“需要时”作为触发条件。正文中的适用条件必须与元数据一致。

## 4. 整理各项目的规则

在每个项目会话分别发送：

```text
使用 manage-obsidian-project-kb，按新版协议整理当前项目知识库中的项目／模块规则。
本次授权修改当前项目的规则笔记和 Dashboard Rule Catalog。

先建立可恢复备份，依据原有内容补齐类型、加载时机和触发条件，
保持原有行为要求、强度与实际适用范围，不改变历史事实。
ADR、Runbook 和排错记录保留各自结构；临时范围、阶段例外、待办和阻塞
继续留在事项文档、Sprint、Worklog，不升级为全局规则。
含义不明确的规则保持原状并报告，不修改其他项目，也不重新整理 Shared。
同步来源、Change Log 和 Catalog，读回验证并报告结果。
```

目录结构不需要重建。可以先整理当前活跃模块，其他规则保持兼容；不要求一次补齐所有历史笔记。授权范围中的实际知识变更按 Skill 规则记录 Worklog，纯诊断和场景推演不记成完成成果。

## 5. 验收是否达到预期

先开新会话进行只读验证，避免旧会话中已经加载的全文影响判断：

```text
使用 manage-obsidian-project-kb，只读验证当前项目的规则加载。

分别以“检查 README 文案”“修改鉴权接口”“准备数据库迁移”为场景，
报告应加载的规则来源和原因、明确不适用的条件规则，以及未解决的兼容项。
再检查任务从文档查询转为迁移规划时，是否会补读新命中的规则。
核对来源与 Catalog，区分实际读取结果和场景推演结论。
不要修改文件，不运行构建、部署或迁移，不写 Worklog。
```

| 检查项 | 通过标准 |
|---|---|
| 文档任务 | 已明确不适用的构建/部署/迁移规则不读全文；常驻和旧兼容规则仍读取 |
| 范围变化 | 新增鉴权、构建或迁移操作前，补读实际命中的规则 |
| 规则完整性 | Catalog 漏项/过期不能隐藏来源规则；命中超过 5 条时不截断 Mandatory |
| 不明确条件 | 报告歧义并读取来源确认，不能默认“不适用”或伪称已遵守 |
| 幂等初始化 | 重复执行时，无差异配置和桥接零写入、零重复区块、零无效备份 |
| 日常完成同步 | 在后续真实开发任务完成后，用 `/kb-status`、`/kb-today` 核对任务状态和结果证据 |

验收以相关规则是否命中、无关正文是否减少为准，不承诺固定的 token 降幅或“绝对不会遗漏”。元数据发现仍有读取成本。结构校验只能检查 Skill 包格式，不能代替实际客户端行为验证；Markdown 也不能替代账号权限、CI 契约检查等执行控制。

## 常见问题

**更新了 Skill，为什么每次还是读很多？**

检查实际加载的 Skill 路径、项目桥接版本和旧 Mandatory 数量。旧规则没有 load 时会继续全文读取；仅升级桥接不会完成规则迁移。还要检查客户端的其他指令文件是否保留了旧的“每次全部加载”要求，定位后按其管理边界处理，不直接覆盖用户指令。

**`/kb-doctor` 没有自动修好 Catalog？**

它是只读诊断。使用第 3/4 步的明确整理任务进行来源与索引同步，不只修改 Catalog 来改变实际约束。

**能否一次更新所有项目？**

可以让 Agent 按你明确列出的项目路径逐个处理。每次重新读取该项目配置，逐项记录成功/失败；多个 Vault 的 Shared 分别整理，同一个 Shared 不重复迁移。先完成一个项目的验收，再推广。

## 部分失败与回退

- 保留每次升级的文件清单、备份位置和未完成项。某个目标失败时只重试该范围，不把部分成功报告为整体成功。
- 仅 Skill/桥接升级需要回退时，恢复已备份的完整 Skill 包，并恢复对应项目的托管桥接区块；如果文件已有后续用户修改，按差异恢复区块，不能整文件覆盖新内容。
- 已整理过规则时，回退客户端不会撤销知识库变化。旧客户端可能忽略 Conditional 而重新加载全部 Mandatory。需要回退知识时，按变更清单恢复相关元数据、正文与 Catalog，并保留迁移后的快照及审计说明。
- 不用旧 Vault 全量覆盖来修复少数规则，也不删除原始历史。回退后重新执行只读诊断，核对实际加载路径和配置兼容性。
