# One-request upgrade

在 `/kb-upgrade` 或用户要求“一次完成 Skill、项目与知识库升级”时读取。本文件编排现有初始化、规则迁移和诊断流程；不是独立的 Shell 安装器。`/kb-upgrade --check` 全程只读，只输出发现和计划。

## Scope and interaction

- 默认范围：当前会话实际使用的 Skill 安装、当前代码项目配置的客户端桥接、该项目的知识目录及其 Shared 规则。Shared 影响同一 Vault 的其他项目，但不自动访问或修改其他代码仓库、其他客户端的独立安装或其他机器。
- 一次请求包含上述兼容性整理授权；简短说明范围后连续执行，不逐步询问、不要求用户手动接力运行 `/kb-init`、整理提示词和 `/kb-doctor`。
- 仅在关键来源或目标身份无法确定、宿主要求权限时请求所需信息/审批。规则迁移中的歧义不逐条打断：保留原规则与兼容加载，完成独立且可安全推进的项，最后集中报告。
- 若不可读的 Mandatory 无法排除与升级操作相关，遵循规则加载协议暂停受影响写入；不得以“升级”为理由绕过现有约束。不要把只读检查或计划视为允许执行升级。

## 1. Identify source and installed target

解析 Project_Root，读取实际加载的 SKILL.md 及当前项目配置，识别安装方式（复制、软链接、项目内安装或客户端管理）。读取 `references/agent-adapters.md`、`references/rule-loading.md` 和升级涉及的 Markdown 模板。

发布来源按用户指定来源、该 Skill 安装记录/当前项目的 `.ai/kb-backups/upgrades/source.json`、Skill 自身仓库 remote 的顺序确定；不能把当前业务项目的 origin 当成 Skill 来源。若来源不明，只询问一次仓库 URL 或新版包路径，不猜测同名仓库。用户已指定本地新版包时可直接使用，并标注“本地版本”，不声称是 GitHub 最新版本。

网络可用时解析该来源的最新稳定 Release 到具体标签/提交；没有 Release 时使用已确定的来源默认分支并记录提交 ID，明确它是分支版本。用户指定版本优先。下载完整 Skill 包到临时目录，检查 name、必需资源、模板及目标升级说明；不直接执行网络内容中的安装命令。不能联网或查不到版本时，可继续将现有安装协议应用到项目，但最终将“最新版核对/安装”标为 Pending，不能声称完成最新版本升级。

“远端最新”可能早于本机未发布版本。核对发布版本、已记录提交及桥接/配置协议，不以下载时间判断新旧；目标缺少当前升级协议或明显更旧时，不自动降级。无法比较且本地存在定制/未发布改动时保留当前包并报告安装 Pending，可按当前协议完成无冲突的项目升级。

## 2. Back up and update the package

先比较实际内容，仅有差异时保存完整旧 Skill 包及受影响文件清单到客户端不会扫描的私有备份目录。保留可追溯的目标版本与来源；备份中可能含本机路径，不写入可提交文档。

- 复制安装：在备份和校验后替换目标包；保留用户定制差异，不直接以新包覆盖无法合并的修改。
- 软链接：更新已确定的链接目标；脏工作树不得 reset/强推。不能安全更新时报告冲突，不悄悄切换安装位置。
- 客户端管理安装：优先使用其可用的更新入口；不可自动操作时明确报告安装未完成。
- 只处理本次已确定的实际安装，不扫描并覆盖所有同名目录。独立的其他客户端安装列入剩余事项。

读回新版包。若包内容已更新，重新读取其中的 SKILL.md、升级协议与模板再处理项目，避免继续执行旧会话缓存的迁移规则；继续受用户本次授权范围约束。需要客户端重启才能发现新资源时说明这一限制，不承诺能让宿主即时热重载。

来源信息待补充、联网失败或安装权限被拒绝时，仅将包步骤标为 Pending；现有包经核对仍完整可用时，可继续当前协议支持、无依赖冲突且已授权的项目步骤。包部分写入或完整性不明时暂停依赖项，先根据备份恢复或修复一致的包；不把新旧协议混合使用，不擅自换安装路径绕过权限。

## 3. Reconcile the current project

按 `/kb-init` 运行已有配置校验、Git 本地忽略、目录及桥接对账。保持 Vault、Project_Name 和 Agent_Clients 选择；Schema 0/1 按协议备份后迁移，Schema 2 无需改写。适用标准区块更新至当前模板版本；导入桥接验证其导入目标，不能要求所有导入文件都有同一个版本标记。

配置缺失时先进行初始化向导取得必要的 Vault/项目选择，不猜测绑定。如果某个目标失败，报告部分状态并只继续无依赖的步骤。

成功确定来源且完成 Git 本地忽略检查后，可将已验证的 `source`、`installed_path`、`revision` 保存到项目本地 `.ai/kb-backups/upgrades/source.json`，供后续升级复用；值相同时不写入。该记录不替代实际文件校验，不保存凭据或带认证参数的 URL，不打包进可分发 Skill。--check 不创建记录。

## 4. Migrate rules conservatively

在已有锁顺序下处理 Shared，然后处理当前项目。修改前把来源笔记与索引保存为不覆盖的私有备份，核对内容未被其他 Agent 改动后再打补丁。

- 从现有规则正文提取已经明确的操作、模块、路径和环境条件，补齐 kind/load/triggers；条件明确时可将旧兼容加载迁移为 Conditional。这是本命令已授权的兼容性整理，不需每条重新确认。
- 保持实际适用范围、行为要求、enforcement 和 status 不变。始终适用的规则标记 Always；无法确定的旧 Mandatory 不写猜测的 triggers，继续兼容加载并列入待确认项。
- 已经有合法加载元数据且正文一致的来源保持不变，Catalog 独立对账；中断后来源已更新、索引未更新时仍须修复索引。保留原文历史，必要时局部补充验证/例外/证据说明；未知证据写未验证，不能编造。
- 类型判断明确时补 kind，但不得通过改类型移除原有强制要求。非规则知识只在整理必需时补类型，不重写全部 ADR、Runbook 或故障笔记。
- 同步来源、Change Log 与对应 Rule Catalog。对每个文件比较实际与期望内容，只有内容无差异才不写入或备份；即使业务语义不变，实际元数据迁移仍须备份并记录一次 Change Log。已记录的同一迁移不重复追加，Catalog 按来源去重。
- 不自动合并/废弃、降低强度、扩大项目范围、清除锁或执行知识笔记中的运维命令。这些不属于兼容升级。

Shared 在另一个项目升级时若已迁移且内容一致，自动 no-op，无需用户记住“共享层做过没有”。只看当前文件实际内容，不能依赖某个项目的升级成功标记来跳过检查。

## 5. Verify and report once

执行 `/kb-doctor`，读回配置、所有桥接和本次修改的规则/Catalog。检查标记唯一、未托管内容保留、条件与正文一致。再次计算同一升级的预期变更，确认已完成部分无差异；不要为了证明幂等性反复下载包、写备份或日志。

进行只读加载场景核对：文档任务跳过明确无关的条件规则，新增构建/迁移计划触发补读，旧 Mandatory 保持兼容，Catalog 漏项及超过 5 篇的命中规则不被截断。报告这是场景核对，不把它说成实际部署或完整客户端端到端测试。

实际持久变更按 Automatic Worklog 的稳定事件 ID 去重记录一次；完全无变化或 --check 不产生工作事件。中断后再次 `/kb-upgrade` 时重新检查实际内容并完成剩余项，已完成文件保持 no-op，失败项不能被整体成功标记掩盖。

若上次已完成持久变更但漏记日志，仅在 Change Log 等证据明确原日期、结果且事件尚不存在时，复用 `/kb-log --reconcile` 规则补录并标记 Reconstructed；不改成今天的新成果。证据不足时只报告待补录，不能凭现有版本推断曾经发生的升级事件。--check 始终只报告，不补录。

最终只给一份简短结果：包来源/实际版本、项目桥接、Shared、项目规则、验证、备份位置，以及需用户处理的少量剩余项。区分 `Completed`、`Already current`、`Pending`；存在未完成项时使用“升级部分完成”，不能仅因桥接成功而说知识库全部迁移完毕。
